# Excluded Folders

This is the one skip list.

Source of truth: `icm.defaults.json`, keys `excluded_globs` and `never_write`. This file is
the human readable rendering of those two keys plus the rules for using them. If this file
ever disagrees with `icm.defaults.json`, the JSON is right and this file is a bug.

**No script reads this document.** Every script reads the two keys out of the JSON at run
time, and no prose anywhere else may restate the list: not in a SKILL.md, not in a script
comment, not in an interview template. A second copy of a skip list is a copy that goes stale,
and a stale skip list is how a scanner ends up walking `node_modules` and reporting three
thousand budget breaches. The renderings below are for your eyes; they are checked against the
JSON, never consulted by a program.

---

## Two Lists, Two Meanings

They overlap. They are not the same list and they do not do the same job.

| List | Meaning | Applies to |
|---|---|---|
| `excluded_globs` | Do not descend into this. Do not scan, index, count, lint, or map it. | Reading |
| `never_write` | Do not create, modify, move, or delete anything inside this. Ever. | Writing |

A path in `excluded_globs` is invisible to every scan. A path in `never_write` is untouchable
by every write, including a write the user asked for by mistake.

`never_write` is the stricter list and it is not subject to the collision rule. Everywhere
else in this toolkit, a collision with an existing user file goes to `.icm/proposed/` for the
user to diff and decide. Inside a `never_write` path there is no proposal and no diff. The
answer is no, and the script says which rule refused.

## `excluded_globs`

Twenty-one entries. Do not descend into any of them.

```
# icm:excluded-globs:begin
.git
.github
.claude
.icm
.in_use
node_modules
venv
.venv
__pycache__
.pytest_cache
dist
build
out
.next
.nuxt
.cache
vendor
target
.terraform
coverage
.DS_Store
# icm:excluded-globs:end
```

They group into four kinds.

**Tool state.** `.git`, `.github`, `.claude`, `.icm`, `.in_use`. Machinery, not workspace. `.in_use` is the lock directory a Claude Code plugin install writes at the plugin root while a session has it loaded. `.claude`
holds harness configuration that the user owns. `.icm` holds this toolkit's own plan,
backups, and proposals, and a scanner that walks it would find the proposals it just wrote and
report them as real files.

**Dependency trees.** `node_modules`, `venv`, `.venv`, `__pycache__`, `.pytest_cache`,
`vendor`. Other people's code. Enormous, and none of it is yours to lint.

**Build products.** `dist`, `build`, `out`, `.next`, `.nuxt`, `.cache`, `target`,
`.terraform`, `coverage`. Generated. Regenerated by a build, which means anything a scan says
about them is out of date the next time someone runs one.

**Noise.** `.DS_Store`. A file, not a folder, and it is on the list so it never turns up in a
listing.

Names, not paths. `node_modules` matches at any depth. This matters for nested dependency
trees and for monorepos where the same folder name appears in a dozen places.

---

## `never_write`

Nine entries. Never write inside these, under any circumstance.

```
# icm:never-write:begin
.git
node_modules
venv
.venv
__pycache__
dist
build
.next
.claude
# icm:never-write:end
```

Every one of these is also in `excluded_globs`, so nothing here is ever scanned either.

Why this list is shorter than the other one: exclusion is about wasted effort, and refusal is
about damage. Scanning `coverage` is pointless. Writing into `.git` corrupts a repository.
Writing into `.claude` changes the user's harness configuration, which is theirs and not this
toolkit's to touch. Writing into `node_modules` or a build folder produces a change that
silently disappears at the next install or build, which is worse than failing, because it
looks like it worked.

**No skill and no script in this toolkit writes to a `never_write` path.** Not even when
asked. If a user request would require it, refuse and say which path and which rule.

---

## What an Entry May Hold

An entry in either list is a name, or a glob on a name. It uses one alphabet: letters, digits,
`.`, `_`, `*`, `?` and `-`. No slash, no space, no quote, no `$`, no bracket. To match a name
with a space in it, write `?` where the space goes, so `Copy?of*` matches `Copy of notes`.
An `excluded_globs` entry is tested against each name the walk meets. A `never_write` entry is
tested against each component of the path about to be written.

Every script checks every entry each time it loads a defaults file, before it walks or writes
anything. An entry outside the alphabet is a refusal: exit 2, and a `FAIL` line that names the
key and the entry's place in it.

The reason is that a workspace `icm.defaults.json` is committed data, and anyone can hand you
one. Nothing read from it may become shell or `find` syntax. No script passes an entry through
`eval` or builds a `find` expression string from it. Each entry is one quoted argument, the
operand of `-name`, so even an entry spelled `-delete` stays a name. An entry is tested
against the names under the target, never the target's own name, so a workspace in a folder
called `build`, or an entry `.*`, still has its tree walked.

## Using the List in a Script

Two supported ways. Both are POSIX. Pick one and never hand type the globs.

### Extract the list from this file

The machine blocks above have stable begin and end markers, so a script can read them:

```sh
sed -n '/^# icm:excluded-globs:begin$/,/^# icm:excluded-globs:end$/p' \
  spec/excluded-folders.md | sed '1d;$d'
```

That prints one glob per line, with the marker lines stripped. The same works for
`never-write` with the other marker pair. Do not reformat the machine blocks. One entry per
line, no comments, no trailing spaces. The markers are an interface.

### Copy the prune expression

This is what the expression looks like once the globs are substituted in. It is here so you
can read one, not so a script can copy it. A script passes the same names to `find` at run
time, each one a separate quoted argument, never a string it builds and never through `eval`.
That is why this block can never be the thing that drifts.

```sh
find . \
  \( -name .git \
  -o -name .github \
  -o -name .claude \
  -o -name .icm \
  -o -name node_modules \
  -o -name venv \
  -o -name .venv \
  -o -name __pycache__ \
  -o -name .pytest_cache \
  -o -name dist \
  -o -name build \
  -o -name out \
  -o -name .next \
  -o -name .nuxt \
  -o -name .cache \
  -o -name vendor \
  -o -name target \
  -o -name .terraform \
  -o -name coverage \
  -o -name .DS_Store \) -prune -o \
  -name '*.md' -print
```

How it reads: match any of these names, prune it so `find` does not descend, otherwise print
markdown files. The `-o` after `-prune` is what makes the second branch apply only to things
that survived the first.

Two mistakes to avoid.

**Do not put `-print` on the prune branch.** That prints the excluded folders instead of
skipping them.

**Do not lose the parentheses.** In `find`, `-o` binds looser than the implicit `-a`, so
without the escaped parentheses the prune applies to the last name only and everything else
gets walked.

To act on the results, use `-exec ... {} +` rather than piping to `xargs`, so paths containing
spaces survive:

```sh
... -name '*.md' -exec wc -c {} +
```

## Refusing a Write

A script that is about to write checks the destination against `never_write` first. The check
is on any path component, not just the first, because a `never_write` name can appear at any
depth.

The names are never typed into the test. They are read from `icm.defaults.json` and matched
one at a time:

```sh
# $1 is the relative path about to be written. Prints the entry that
# refuses it, or nothing when it may be written.
icm_never_write_hit() {
    _wh_list=$(icm_json_list "$ICM_DEFAULTS" never_write)
    _wh_p="$1"
    while [ -n "$_wh_p" ]; do
        _wh_c=${_wh_p%%/*}
        case "$_wh_p" in
            */*) _wh_p=${_wh_p#*/} ;;
            *)   _wh_p="" ;;
        esac
        [ -n "$_wh_c" ] || continue
        while IFS= read -r _wh_g; do
            [ -n "$_wh_g" ] || continue
            case "$_wh_c" in
                $_wh_g) printf '%s\n' "$_wh_g"; return 0 ;;
            esac
        done <<EOF
$_wh_list
EOF
    done
}
```

Three details do the work. Each component is cut off with `${p%%/*}` and `${p#*/}`, which is
parameter expansion, not word splitting, so a component with a space in it stays whole. Each
component is matched against each entry as a `case` pattern, so a wildcard entry such as `_l*`
refuses `_log/x.md`. And the entries are read one per line with `read -r`, never with
`for x in $(...)`, so the shell never expands an entry against the cwd it happens to run in.

`scripts/icm_lib.sh` holds that function, and `icm_never_write_ok` is true when it prints
nothing. Every script calls them. The names live in the JSON
and nowhere else, so there is no fragment here for a script to copy and no second list to go
stale. A refusal names the path and the rule that refused it.

## Adding to the List

The list changes in `icm.defaults.json` first, then here, then nowhere else, because there is
nowhere else.

Before adding an entry, check it against the four kinds above. If a folder is not tool state,
not a dependency tree, not a build product, and not noise, it probably belongs in the
workspace and the real problem is that it is in the wrong place.

Adding to `never_write` needs a stronger reason than adding to `excluded_globs`. Ask what
breaks if a file is written there. If the honest answer is "nothing, it is just untidy", it
belongs in `excluded_globs` alone.

### One workspace's own list

The list above is the toolkit's. One workspace can change its own list without touching the
toolkit: put an `icm.defaults.json` at the workspace root holding the key. The toolkit's file
loads first and the workspace file overlays it key by key, so a key the workspace file lacks
still comes from the toolkit. A list is the exception to that: a workspace `excluded_globs` or
`never_write` replaces the toolkit's list whole. Start from a copy of the toolkit's entries you
still want, then add yours. An entry in the workspace file is held to the same alphabet, and
the refusal names that file. `spec/CLI-CONTRACT.md` section 3.0 holds the whole merge rule.

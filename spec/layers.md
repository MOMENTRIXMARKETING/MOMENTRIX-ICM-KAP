# The Layers

This file defines every layer precisely. It is authoritative. `spec/CONVENTIONS.md` gives the
methodology around them, `spec/budgets.md` gives their sizes, and both defer to this file for
what a layer actually is.

Six slots. Five layers, because layer 4 splits in two.

| Layer | Where | Question | Owner | Changes |
|---|---|---|---|---|
| 0 | `IDENTITY.md` | Where am I? | Human | When the structure changes |
| 1 | `CONTEXT.md` at a folder root | Where do I go? | Human | When routes change |
| 2 | `CONTEXT.md` in a stage, the job card | What do I do? | Human | When the process changes |
| 3 | `_config/` rule books | What rules apply? | Human only | When doctrine changes |
| 4a | `raw/` | What is true? | Nobody, it is immutable | Only by adding files |
| 4b | `wiki/` and `output/` | What do we know, what did we make? | The agent | Every run |

---

## Layer 0: IDENTITY.md

One per workspace. At the workspace root. Always loaded.

It answers "where am I" and nothing else. It contains:

- The workspace name and one sentence saying what it is for
- `## Workspace Map`, a folder tree with a one line comment per entry
- `## Rules`, the handful of standing rules that apply everywhere in this workspace

Those two headings are required. `icm.defaults.json` lists them under
`required_sections."IDENTITY.md"`.

It does not contain routing. Routing is layer 1. It does not contain doctrine. Doctrine is
layer 3. If `IDENTITY.md` is telling you how to write, something has leaked upward.

**Model agnostic by design.** Layer 0 is `IDENTITY.md` in every workspace, whichever agent
harness reads it. Harness files, `CLAUDE.md`, `.cursorrules`,
`.github/copilot-instructions.md`, `.windsurfrules`, are **aliases**. An alias points at
`IDENTITY.md`. It never restates it.

```markdown
<!-- Alias. The workspace identity lives in IDENTITY.md. Do not edit this file. -->
@./IDENTITY.md
```

Where the harness has no import mechanism, the alias holds one instruction instead:

```markdown
<!-- Alias. Do not edit this file. -->
Read `IDENTITY.md` at the workspace root before doing anything else. It is layer 0.
```

An alias that has grown a folder map has become a copy, and a copy is a bug. There is nothing
to sync, because there is nothing duplicated.

**Layer 0 does not recurse.** A department does not get its own `IDENTITY.md`. If a folder
feels like it needs one, it is a separate workspace, not a department.

**Read from the other side: a folder that holds an `IDENTITY.md` is a workspace root.** That
is what lets one repository carry a whole workspace inside it, a worked example, a vendored
project, two workspaces in one monorepo. The checker reads it the same way. A `CONTEXT.md`
sitting beside an `IDENTITY.md` is that workspace's layer 1, graded against the layer 1 budget
and the layer 1 section list, and the tree beneath it is documented by its own `IDENTITY.md`
rather than by the outer one. To grade the inside of a nested workspace, run the checker on
that folder.

## Layer 1: CONTEXT.md, routing

The first file an agent reads after `IDENTITY.md`. It answers "where do I go".

Required headings, from `icm.defaults.json` under `required_sections."CONTEXT.root.md"`:

- `## Routing`, a table mapping task type to destination
- `## Session Start`, the numbered steps for entering this workspace
- `## Rule Books`, what lives in this folder's `_config/` and when each applies

The routing table is the whole point:

```markdown
## Routing

| Task | Go to | Load first |
|------|-------|------------|
| Write to a prospect | `departments/sales/CONTEXT.md` | nothing else yet |
| Plan a campaign | `departments/marketing/CONTEXT.md` | nothing else yet |
```

Note the third column. Layer 1 tells you where to go, and it tells you not to load anything
on the way. The job card at the end of the route decides what gets loaded. Loading rule books
speculatively at layer 1 is the single most common way a workspace blows its budget.

**Layer 1 recurses.** Every department gets one. See the recursion section below.

---

## Layer 2: CONTEXT.md, the job card

A `CONTEXT.md` inside a stage folder. It answers "what do I do". It is called a job card. Not
a skill, not a prompt, not a spec.

Required headings, from `icm.defaults.json` under `required_sections."CONTEXT.stage.md"`:
`## Purpose`, `## Inputs`, `## Process`, `## Outputs`, `## Routing`. Optional: `## Checkpoints`
and `## Audit`.

**Layer 2 is the control point of the entire system.** Its Inputs table decides exactly which
layer 3 and layer 4 files enter the context window. Nothing else decides. An agent under this
methodology does not search for context. It reads paths off a table.

```markdown
## Inputs

| Source | File/Location | Section/Scope | Why |
|--------|--------------|---------------|-----|
| Rule book | `../../_config/objections.md` | "Price" and "Timing" | The two objections this stage answers |
| Rule book | `../../../../_config/voice.md` | "Banned words" | What we may never say |
| Prior stage | `../01-qualify/output/lead-brief.md` | Full file | Who we are writing to |
```

Every row names a section unless the whole file is genuinely needed. Every row says why, so a
reader can tell whether the row is still earning its place.

A job card has a line ceiling as well as a char ceiling. Both are in `spec/budgets.md`. The
line ceiling exists because job cards fail by growing content, and content grows in lines
before it grows in chars.

---

## Layer 3: `_config/` rule books

Files in a `_config/` folder. They answer "what rules apply".

**They are rule books. They are never called skills.** A skill is a folder under `skills/`
with a `SKILL.md` and frontmatter. A rule book is a markdown file in `_config/` holding a
human's ruling. Different owners, different budgets, different authority.

A rule book states the rule first and the reason second. The rule is what gets applied under
load. The reason is what stops the rule being ignored the first time it is inconvenient.

**Only a human edits a rule book.** No script writes to `_config/`. No skill writes to
`_config/`. An agent that believes a rule book is wrong or incomplete writes a proposal to
`_log/FORGE-PROPOSALS.md` and stops. `spec/authority-model.md` says why.

**Rule books are not evidence checked.** The grounding invariant binds `wiki/`, which is
compiled from sources. A rule book is a decision. A person decided it, so there is no raw
file behind it and none is required.

**Layer 3 recurses.** A company has `_config/` and each department has its own. A job card may
name rule books from its own department and from the company. It may not name another
department's.

When a `_config/` folder holds more than about ten files, add `_index.md` and let job cards
point at the index instead of guessing.

## Layer 4a: `raw/`

Immutable source material. It answers "what is true".

One `raw/` per workspace, at the root. Organised by topic subdirectory, one level:
`raw/<topic>/YYYY-MM-DD-slug.md`.

Four rules.

**Nothing ever edits a file in `raw/`.** Not to fix a typo, not to reformat, not to update.
The only legal write to `raw/` is adding a new file.

**Every raw file carries its provenance header**: where it came from, when it was collected,
when it was published. Published unknown is written as `Unknown`, never guessed.

**`raw/` does not recurse.** A source is a source regardless of which department cites it.
Copying a source into a department's own `raw/` gives the same fact two homes, and two homes
is how the grounding invariant breaks.

**`raw/` is cited, not loaded whole.** A job card that says "read all of raw/" has
misunderstood the layer. An agent opens the specific raw files that the article or the job
card links, and it opens them to locate a specific literal.

Immutability is not fussiness. It is what makes verification cheap. A verified article stays
verified forever, because the evidence underneath it cannot have moved. That is why the
whole wiki can be re checked in seconds and why there is no incremental verification state to
maintain anywhere.

## Layer 4b: `wiki/` and `output/`

Compiled and produced. Two folders, two lifetimes, one layer.

### `wiki/`, compiled, durable

What we know. Articles compiled from `raw/`, owned by the agent, surviving across runs.

```
wiki/
├── index.md          one row per article, grouped by topic
├── log.md            append only operation log
└── <topic>/
    └── <article>.md
```

One level of topic subdirectory. No deeper nesting.

Every article carries a `Raw:` field linking the raw files it was compiled from. Every load
bearing fact in the article exists verbatim in one of them. That is the grounding invariant
and `spec/grounding-invariant.md` is authoritative on it.

`wiki/` compounds. It is the part of the workspace that gets more valuable the longer it
runs, and it is the reason `raw/` is immutable.

### `output/`, produced, per run

What we made. One `output/` per stage. Written by the stage, read by the next stage, replaced
next run.

```
stages/02-write-outreach/output/acme-outreach-draft.md
```

An `output/` file is an edit surface. A human can open it, change it, save it, and the next
stage picks up the change. It is not a source of truth and it is not a template. Agents do
not read other stages' outputs to learn patterns. Rule books are where patterns live.

### Why 4a and 4b are separated

They differ on the only axis that matters for trust.

| | 4a `raw/` | 4b `wiki/` and `output/` |
|---|---|---|
| Written by | The world, captured once | The agent |
| Mutable | Never | Yes |
| Answers | What is true | What we know, what we made |
| Role in verification | The evidence | The thing being verified |
| Lifetime | Forever | `wiki/` compounds, `output/` is per run |

Collapse them back into one layer 4 and you lose the ability to ask any claim where it came
from, because the answer might be another claim.

## Recursion

Layers 1, 2, and 3 repeat inside each department. Layers 0 and 4a do not.

A company workspace holds departments. Each department repeats the pattern inside itself.

```
acme/
├── IDENTITY.md                       layer 0, one for the whole workspace
├── CONTEXT.md                        layer 1, company routing
├── _config/                          layer 3, company rule books
│   ├── voice.md
│   └── evidence-rules.md
├── raw/                              layer 4a, one for the whole workspace
│   └── market/2026-04-02-industry-survey.md
├── wiki/                             layer 4b, compiled
│   ├── index.md
│   ├── log.md
│   └── market/pricing-benchmarks.md
├── _log/                             ledger, run logs, forge proposals
└── departments/
    ├── sales/
    │   ├── CONTEXT.md                layer 1 again, sales routing
    │   ├── _config/                  layer 3 again, sales rule books
    │   │   ├── objections.md
    │   │   └── pricing.md
    │   └── stages/
    │       ├── 01-qualify/
    │       │   ├── CONTEXT.md        layer 2, job card
    │       │   └── output/
    │       └── 02-write-outreach/
    │           ├── CONTEXT.md        layer 2, job card
    │           └── output/
    └── marketing/
        ├── CONTEXT.md                layer 1 again, marketing routing
        ├── _config/                  layer 3 again, marketing rule books
        └── stages/
            └── 01-plan-campaign/
                ├── CONTEXT.md
                └── output/
```

The chain, written out:

```
company CONTEXT.md  ->  company _config/
        |
        v
department CONTEXT.md  ->  department _config/
        |
        v
stage CONTEXT.md (job card)  ->  the rule books this job names, from either _config/
```

Rules of the recursion:

1. A department's `CONTEXT.md` is layer 1 for that department. It has the same three required
   headings as the root one, scoped to the department.
2. A department's `_config/` holds only rules specific to that department. Anything two
   departments both need moves up to the company `_config/`. That is canonical sources
   applied to the tree.
3. A job card may name rule books from its own department and from the company. It may never
   name another department's.
4. References point down the layers and up the tree. Never sideways, never back up into a
   stage. A company rule book never mentions a department.
5. One `IDENTITY.md`, one `raw/`, one `wiki/`, one `_log/`. Those live at the workspace root
   and are shared.
6. Depth costs. Every level between the root and the job card is one more file every task in
   that department must read, forever. Keep departments one level deep unless there is a real
   reason for two.

## Read Order: One Task, One Department

The task: write outreach to a qualified lead. The agent has just been handed it and knows
nothing.

**File 1. `acme/IDENTITY.md`** (layer 0)

It learns where it is: this is the Acme workspace, departments live under `departments/`,
`raw/` is immutable, `_config/` holds rule books, and the standing rules of the house.

**File 2. `acme/CONTEXT.md`** (layer 1, company)

It reads one row of the routing table:

```
| Write to a prospect | departments/sales/CONTEXT.md | nothing else yet |
```

It goes there. It does not open `_config/voice.md`, even though the company `Rule Books`
section mentions it, because the third column said not to.

**File 3. `acme/departments/sales/CONTEXT.md`** (layer 1, department)

It reads one row:

```
| Outreach to a qualified lead | stages/02-write-outreach/CONTEXT.md | nothing else yet |
```

**File 4. `acme/departments/sales/stages/02-write-outreach/CONTEXT.md`** (layer 2, the job
card)

Now it knows what it is doing. The Inputs table names, by path, exactly what to load next:

```markdown
| Source | File/Location | Section/Scope | Why |
|--------|--------------|---------------|-----|
| Rule book | `../../_config/objections.md` | "Price" and "Timing" | The two this stage answers |
| Rule book | `../../../../_config/voice.md` | "Banned words" | What we may never say |
| Prior stage | `../01-qualify/output/lead-brief.md` | Full file | Who we are writing to |
| Wiki | `../../../../wiki/market/pricing-benchmarks.md` | "Current benchmarks" | The numbers we may cite |
```

Four files to get from "where am I" to "what do I do". Then, and only then, the named layer 3
and layer 4 files.

Path arithmetic from the stage folder: `../../` reaches `departments/sales/`, and
`../../../../` reaches the workspace root. Every job card in a department at this depth uses
those two prefixes, which is the practical reason to keep departments one level deep.

**What the agent never loads:**

- Anything under `departments/marketing/`. It never opened that folder and never will.
- `departments/sales/stages/01-qualify/CONTEXT.md`. It only read that stage's output, because
  the job card named the output, not the job card.
- `departments/sales/_config/pricing.md`. It sits right beside a rule book that was named,
  and it was not named, so it is not loaded.
- The rest of `_config/voice.md` outside the "Banned words" section.
- All of `raw/`, except the one file linked from the wiki article, opened only to confirm a
  number before writing it.

Sibling departments are invisible. Sibling stages are invisible. Unnamed rule books in the
same folder are invisible. That invisibility is the product. It is not a side effect of the
folder layout, it is the thing the folder layout is for.

**What it costs.** The four routing files plus the rule books is the fixed load for this task.
`spec/budgets.md` shows the arithmetic, including the surcharge the department level adds over
a flat workspace.

## What Each Layer Must Never Do

| Layer | Must never |
|---|---|
| 0 | Hold routing, doctrine, or anything a department owns |
| 1 | Hold reference content, or tell an agent to preload rule books |
| 2 | Hold the rules themselves instead of pointing at them |
| 3 | Be edited by anything other than a human |
| 4a | Be edited at all |
| 4b | Be treated as a source of truth or as a template |

Every one of these failures looks the same from outside: the workspace still works, and every
task quietly costs more context than it should, until one day the job cards stop fitting and
nobody can say when that started.
